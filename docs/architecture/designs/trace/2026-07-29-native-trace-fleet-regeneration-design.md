# Native Trace Fleet Regeneration Design

## Objective

Regenerate every canonical trace fixture that has a reproducible native
BizHawk recording input, using the current `tools/bizhawk-headless` build.
Measure the replay frontier of every executable `*TraceReplay` test against the
proposed fleet and report a complete class-by-class result.

The regenerated fleet is also the all-game load-timing audit:

- S1/S2 level rows record physical Nemesis PLC queue state, and all S1/S2
  level/special-stage rows record player dynamic-art preparation/submission/
  completion timing under the reviewed game-specific lifecycle contracts.
- S3K records both complementary Kosinski views: schema-2 hardware timing for
  exact module/direct completion boundary, ordinal, and stable submission
  fingerprint; and end-of-logical-frame physical queue state for both
  `s3k_kos_module` and `s3k_kos_direct`.
- Queue/timing data is comparison-only except for the repository's separately
  guarded hardware-readiness contract, which can release only matching,
  production-submitted S3K work.

## Scope

The canonical inventory reconciles three independent views:

- every payload-bearing fixture directory below
  `src/test/resources/traces/{s1,s2,s3k}`, excluding `synthetic`;
- every BK2, run manifest, native publication identity, and expected segment
  shape;
- every concrete gameplay replay test's resource reference.

Any unmatched or malformed item fails inventory closure. Fixtures are grouped
by recording invocation rather than directory because complete-run and
run-mode movies publish many segments.

Fixtures without a repository BK2 or a supported native recorder mode are
reported as non-regenerable, with their existing recorder/version and reason.
They are not silently copied into the proposed fleet and are not described as
regenerated. This currently applies to the eight S1 credits-demo fixtures
stamped `credits-retro-1.4`.

## Capture and publication boundary

All native captures go to a new `.scratch/trace-fleet-regeneration-*` root in
the isolated worktree on the disk-backed repository filesystem. Preflight
records filesystem type and free bytes and requires enough room for the
estimated peak plus a 25% margin. Captures run serially because the full
complete-run invocations are memory- and disk-heavy. The canonical tree remains
read-only while capture correctness and deltas are assessed.

For each capture invocation, retain:

- the exact command, ROM SHA-1, movie SHA-256, native harness source commit,
  dirty-state/diff hash, built-artifact SHA-256, and exit status;
- the published directory inventory;
- SHA-256 and byte length for every file;
- metadata versions, trace row counts, auxiliary-event counts, hardware-timing
  counts, and run-manifest segment order;
- a structural comparison with the current canonical fixture and a
  byte-level categorized delta ledger.

Before capture, a correctness-evidence section in the publication audit maps
each capture family to its recorder behavior specification, named ROM/disassembly
invariants, and the behavioral and unit tests that prove those semantics.
An independent reviewer checks that evidence and the source implementation and
must report no blocking issues. Committed-fixture byte parity is corroboration
only and cannot certify proposed fixture bytes. Capture stops unless this
semantic review is green.

Audit capability is mandatory and has no canonical opt-out. Every regenerated
S3K fixture uses hardware-timing schema 2 and advertises
`load_queue_state_per_frame`; each trace row has exactly one
`s3k_kos_module` and one `s3k_kos_direct` state at
`END_OF_LOGICAL_FRAME`. Hardware-timing edges remain complementary sub-frame
evidence, not a substitute for physical membership/prepared/remaining-work
state. S1/S2 use their mandatory PLC/DPLC capabilities defined by the reviewed
cross-game load-timing design.
S3K direct-queue destinations use the recorder's signed 32-bit representation
of sign-extended 68K work RAM. Busy destinations are exactly
`$FFFF0000..$FFFFFFFE` (Java `-65536..-2`); `$FFFFFFFF` / `-1` is the absent
sentinel. Validators reject other negative values and non-RAM destinations.
Comparators preserve the exact 32-bit pattern. Representative AIZ/CNZ/MGZ
captures span `-65536..-12288`.

The harness is then rebuilt immediately before capture from that reviewed
source. Capture is rejected if the source is dirty unless the complete diff is
frozen and independently reviewed. Every invocation records and verifies the
same built-artifact hash.

Before approval, independent publication tests freeze literal SHA-256 digests,
byte lengths, metadata versions, segment inventories, row/event counts,
ordering, and ranges for the proposed fleet. These expectations are written
from the reviewed evidence manifest, not generated by a candidate capture
invocation. Every changed byte belongs to a narrowly described delta category;
any residual or unexplained delta rejects publication.

No captured bytes enter `src/test/resources/traces` until the publication
report identifies the exact proposed bytes and the user approves them.

## Capture matrix

The matrix is derived from fixture metadata and the differential tests:

1. S1 standalone trace-mode movies.
2. S1 complete-run movie with `--trace-profile complete_run`.
3. S1 GHZ maze run movie with its canonical `--run-id`.
4. S2 standalone level-select movies, including the recorded
   `--gameplay-segment` for later acts.
5. S2 run-mode movies with their canonical `--run-id`.
6. S2 standalone special-stage movie
   `s2/special_stage/s2-lvl-select-special-stage.bk2`. Its legacy
   `1.4-s2ss` fixture is distinct from run-mode `ss` segments. The inventory
   phase confirmed the current CLI cannot publish it. Before fleet capture,
   add a dedicated `--trace-profile s2_special_stage` path that ports
   `tools/bizhawk/s2_ss_trace_recorder.lua` semantics, including immediate
   recording of the first `$10` frame. The two execute callbacks have distinct
   roles: `PC_READ_JOYPADS_RETURN` captures input-sample identity and
   `PC_S2SS_POST_RUN_OBJECTS` captures one completed RunObjects pass. Preserve
   the recorder's one-input-sample-per-pass assertion, exact cursor/input
   identity, queue-forward publication on the next eligible non-lag row,
   lag-frame behavior, terminal pending-pass flush at the raw finish
   observation, and callback-failure propagation. Reuse the existing S2 special-stage
   CSV/metadata/aux vocabulary where byte-compatible, but keep standalone
   metadata and timing distinct from run-mode segments. A ROM-backed
   differential gate for this exact BK2 is mandatory. Never substitute the
   halfpipe run's different `ss` bytes.
7. S3K standard AIZ/CNZ/MGZ profiles from their fixture metadata.
8. S3K Sonic+Tails complete-run movie with
   `--trace-profile complete_run`.
9. S3K multi-bonus movie under both canonical run identities required to
   publish the standalone bonus/special-stage fixtures and the nested run.

Every S3K command enables load-queue state and emits schema-2 module plus direct
hardware timing. Candidate validation rejects schema 1, a missing queue kind,
anything other than two queue rows per stored trace frame, invalid prepared/
remaining semantics, or fingerprint/order disagreement between physical queue
state and hardware timing.

This contract includes special-stage segments emitted by the S3K named-run
capture path. `S3KCompleteRunCaptureRunner` owns their stored-row boundary: after
the schema-2 timing engine observes frame end, every stored special-stage row
must write the `s3k_kos_direct` state followed by the `s3k_kos_module` state.
The rule applies without exception to lag rows and to the final stored row; a
results boundary that does not publish a row must not publish queue state.
Special-stage metadata advertises `load_queue_state_per_frame` when and only
when that capture capability is enabled. Sink or writer failure is fatal.
Because this changes the complete-run writer's published metadata/aux
contract, its recorder version advances from `6.38-s3k-completerun` to
`6.39-s3k-completerun` for every segment and the run manifest. Compatibility
normalizers accept only the reviewed whole-fixture transitions:
`6.38-s3k-completerun`/trace schema 7/hardware schema 2 complete-run fixtures
to 6.39/schema 7/schema 2, and the exact canonical
`6.37-s3k-completerun`/trace schema 7/hardware schema 1 fixtures to
6.39/schema 7/schema 2. The latter set is the ten late complete-run segments
(`ddz`, `dez`, `ending`, `fbz`, `hpz`, `lbz`, `lrz`, `mhz`, `soz`, `ssz`)
and both named-run identities. A named-run capture must have one
version/schema identity across every segment and its manifest. Partial or
mixed migrations, and every other predecessor shape, remain rejected.

The all-ROM pre-capture gate may fail only at frozen canonical-byte
comparisons whose audited payload/schema migration is the point of this
publication. Ordinary unit and behavior tests must be green. In particular,
version-stamp assertions follow 6.39; complete-run stdout expectations include
the manifest line that the current CLI publishes; and existing S1 boundary
lifecycle tests must agree with the reviewed submission/completion ownership
contract before capture proceeds.

Discovery of a missing special-stage queue stream invalidates the complete
candidate batch, not just the affected segment. The runner correction changes
the reviewed harness artifact hash, while this audit requires one identical
artifact hash across every invocation. Preserve the rejected captures as
diagnostic evidence, rebuild and re-review the corrected artifact, then
recapture all 32 literal invocations into new, absent output roots. Never mix
pre-fix and post-fix output in the proposed fleet.

Before fleet capture, run the selected full native recorder test suite with
all ROM inputs and BizHawk present. Require zero skips and zero runtime,
semantic, or unclassified failures. The only permitted red results are the
exact enumerated successful-invocation schema-migration refusals described
below; record every selected test and classification.
Diagnostic hook environment variables remain unset.

## Replay measurement

After approval and byte-for-byte installation, run Maven's full
`-Dtest=*TraceReplay` selection with JDK 21 and all three verified ROM paths.
Report concrete invariant, reference-closure, report-policy, start-position,
and bootstrap tests in a non-frontier trace-test section. Separately enumerate
concrete gameplay replay classes; each receives one of:

- `green`: all test methods passed;
- `red`: first divergence frame, field, error count, warning count, and report
  path;
- `error`: no parity frontier was produced because setup/build/runtime failed;
- `not executed`: class has no regenerated or retained valid fixture.

The final frontier list is exhaustive over gameplay replay classes, including
green tests. It also records the fixture recorder version used, so
non-regenerable legacy fixtures cannot be confused with newly captured data.

## Safety and failure handling

The pre-capture native gate exposed two current-baseline incompatibilities from
the latest load-queue comparison work:

1. CNZ and MGZ can execute two direct-Kos module-submission callbacks before the
   next frame-end reconciliation. `HardwareTimingEventEngine` currently rejects
   that ROM-observed ordering whenever the first callback staged a PRE
   retirement. The recorder must preserve every submission and defer completion
   ownership to frame-end without weakening FIFO identity checks.
2. The complete-run and named-run differential metadata/manifest normalizers
   recognize only the older canonical schema shape. Regeneration intentionally
   produces the current load-queue schema, so the pre-publication comparison
   must distinguish an expected whole-fixture schema migration from malformed
   or mixed metadata.

Both are recorder/publication-gate work, not engine trace tuning. Each requires
a focused failing test, a source-of-truth comparison against callback and
frame-end ordering, and another full native gate before capture resumes.

Schema-1 fixtures cannot prove schema-2 direct-authority correctness by
definition. The pre-capture gate may therefore remain red only at an exact,
enumerated schema-migration refusal after the recorder invocation itself exits
successfully. That refusal is not converted into a pass. Scratch capture then
supplies the candidate schema-2 fleet for frozen hash/event validation and
independent review. Any recorder runtime error, semantic-unit failure,
unclassified comparator mismatch, or non-migration gate failure still stops
capture.

An existing output directory, recorder nonzero exit, missing segment, manifest
inconsistency, payload decompression failure, schema guard failure, or
unexplained content delta rejects that capture. A rejected capture is rerun
only after identifying the cause; existing fixtures are never weakened to make
the recorder pass.

S3K direct-queue source and destination fields use signed Java/C# `int` wire
values for 32-bit 68K addresses. `-1` alone is the unknown/idle sentinel;
addresses such as `$FFFFD000` are valid active destinations and must survive
strict candidate parsing and zero-tolerance comparison unchanged.

The point-in-time inventory and publication assessment is staged at
`docs/architecture/audits/trace/2026-07-29-native-trace-fleet-publication.md`;
post-publication replay evidence is staged at
`docs/architecture/validation/trace/2026-07-29-native-trace-frontiers.md`.
The full sweep updates `docs/status/trace-frontier-log.md` with the command,
commit/worktree context, pass/fail, error count, and first-error frame/field
whenever a frontier moves, a green regresses, a fix lands, or the sweep selects
a next target.

Historic frontier evidence is immutable even when it contains machine-local
paths recorded before the portability guard existed. The cross-platform commit
policy validates only newly introduced textual lines relative to the commit
parent for an existing file, while validating the full content of a newly
added file. New machine-local paths still fail. Shell and PowerShell policies
must remain behaviorally identical and a tooling guard pins grandfathered-old/
rejected-new behavior. If an earlier branch commit already rewrote historic
evidence, restoration may use a repository-tracked, path-scoped SHA-256
grandfather manifest containing only hashes of the exact pre-existing lines
from the independently verified baseline. The manifest stores no machine-local
path text. Each path+line hash also records the verified baseline occurrence
count; the final file may not contain that line more times than the allowance,
and each allowance is consumed at most once per occurrence. Only an exact
path+line-hash match within that multiplicity is exempt; any changed, novel, or
replayed duplicate line still fails. The exemption additionally requires the
entire verified baseline prefix to remain byte-identical by stored byte length
and SHA-256. Any deletion, substitution, reorder, or later replay invalidates
the exemption; only portable appended evidence may follow the prefix.

The main workspace and its unrelated changes remain untouched. Proposed
artifacts, frozen publication tests, and any later fixture installation live on
`feature/ai-trace-fleet-regeneration` in the isolated worktree. Every relevant
artifact is staged; no report or supporting evidence is left untracked.

## Approved storage normalization

Capture output identity and repository storage identity are separate approval
surfaces. If an approved native payload is plain but repository policy requires
compression, publication must stop before substitution, build a second exact
inventory using deterministic `gzip -9 -n`, prove every decompressed result
byte-identical to the first-approved payload, and obtain explicit approval for
the revised bytes. Uncompressed and compressed siblings must never coexist in
the installed fixture tree. Non-payload files remain byte-identical across the
two inventories.

Publication validation treats plain and compressed siblings as mutually
exclusive. `TraceFiles` intentionally prefers a plain file, so leaving an old
plain sibling beside a newly approved `.gz` would silently replay stale data.
The install reconciles this target closure explicitly and verifies that no
approved compressed target has a plain sibling.

The DPLC lifecycle validator pins ROM callback PCs as capture-integrity
evidence. Regeneration exposed a stale S1 submission whitelist entry:
`$1436A` is a valid decision/arming return callback, but it is not a valid
submitted-edge `rom_callback_pc`. The S1 retail recorder reports submission
sites `$0D20`, `$0E34`, `$0F24`, and `$1030`, paired with completion sites
`$0D50`, `$0E64`, `$0F54`, and `$1060`. Submitted-edge validation accepts
exactly those ROM-owned submission sites while recorder decision observation
continues to accept `$1436A`; this is schema validation, not trace-driven
engine state.

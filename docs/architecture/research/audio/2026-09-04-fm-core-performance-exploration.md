# FM core performance exploration (2026-09-04)

## Decision

Keep the Java Nuked-OPN2 core for this milestone. The experiment found credible
performance opportunities in native Nuked and C++ ymfm, and proved that a
batched Native Image/JNI call can reach native Nuked throughput on this Linux
host, but it did not establish a production-ready replacement. Backend choice,
native lifecycle and distribution, full audio transfer, and fidelity remain
separate engineering work.

This is a point-in-time research record, not release evidence. It preserves the
useful conclusions from the external scratch experiment without committing its
upstream checkouts, downloaded JDK, executables, profiles, raw logs, expanded
register streams, or generated audio.

## Provenance and method

- OpenGGF was launched at `670a37ba94c0807cdf8bf2fa58321e46e9ec0886`
  and finished at `4296bc2915a7d8da0e0ea173427be6e8bbc21812`.
  The synth sources were unchanged from `3295ee9cd` through the finish.
- Host: AMD Ryzen 9 9950X, Linux 7.2.2-1-cachyos, OpenJDK 21.0.11,
  GCC/G++ 16.2.1. The host was not exclusively reserved.
- Nuked-OPN2: commit `335747d78cb0abbc3b55b004e62dad9763140115`,
  tree `6637a500d1da3b08cbc0cec1532ab305197b8978`,
  `LGPL-2.1-or-later`.
- ymfm: commit `81aec25ccbb98f4873a255f7551ac4dadac59b4a`, tree
  `03f76ed27b1281357c91005e99d043eebd5119c1`, `BSD-3-Clause`.
- Each synthetic case used three separate processes. Each process ran three
  warm-ups and ten measured 53,267-frame iterations pinned to CPU 6. Values
  below are the median of the three process medians.
- Synthetic cases were a decaying six-FM patch, a sustained six-FM AM/LFO
  patch, and sustained five-FM plus DAC strobes. They are raw-core workloads,
  not whole-engine profiles.

The original experiment also ran 734 focused OpenGGF tests with zero failures,
errors, or skips: `TestSmpsFadeAudioThroughput`,
`TestNukedOpn2BitExactScripts`, and `TestYm2612ChipSnapshot`. That result used
the verified Sonic 2 REV01 ROM, but the retained benchmark itself is ROM-free.

## Historical results

Nanoseconds per native FM output frame:

| Workload | Java Nuked | C Nuked `-O2` | C++ ymfm `-O2` |
|---|---:|---:|---:|
| Decaying six-FM | 929.9 | 552.7 | 171.0 |
| Sustained six-FM | 917.5 | 554.3 | 170.2 |
| Five-FM plus DAC strobes | 987.1 | 551.9 | 158.6 |

On this host, sustained synthetic work therefore put C++ ymfm at roughly
3.25 times C Nuked throughput and 5.4 times Java Nuked throughput. These are
core-only ratios. The production `Ym2612Chip` facade measured about 5.1 percent
of one host core at both 44.1 and 48 kHz in its synthetic facade probe. Snapshot
capture measured about 1.77 microseconds and 5,448 allocated bytes per capture;
snapshot-every-1,024-output-frames moved the facade probe from about 5.12 to
5.32 percent of one core, below the noise needed for a general claim.

The Java and C Nuked aggregate checksums matched for all nine synthetic process
cases. Fresh snapshot replay was exact for Java Nuked, C Nuked, and C++ ymfm,
and a deliberate channel key-off changed subsequent output in every case. The
repository's 732 independent bit-exact reference cases supply the stronger
sample-level evidence for the Java port; aggregate checksum equality alone does
not.

### Native Image and JNI

Oracle GraalVM 21.0.12+7.1 (archive SHA-256
`b007ff64c425f85bbe0e686107044fba6ca5054a7e89271a473767f546aaddc1`)
was tested separately. Plain Native Image and one-workload user PGO were slower
than HotSpot for all three synthetic profiles. For sustained six-FM, process
medians were approximately 887.9 ns/frame on the host HotSpot, 968.5 on the
Graal JIT, 1,123.1 for compatibility-target Native Image, and 1,073.4 for the
single-profile PGO image. The comparison is directionally useful but confounded
by the host JDK being 21.0.11 while GraalVM carried JDK 21.0.12.

A Native Image executable calling C Nuked through JNI in 1,024-frame batches
matched the Java/C aggregate checksum and measured 537.6 ns/frame. That is the
decisive Linux feasibility result worth preserving: Native Image can cross a
batched JNI boundary without erasing native Nuked's raw-core advantage. It is
not production integration evidence—the JNI method returned one checksum and
did not transfer PCM arrays, schedule audio, resample, snapshot native state,
or exercise teardown and packaging.

### Engine-derived stream diagnostic

Nine existing compressed register fixtures were replayed through both native
cores: six ten-second music excerpts and three SFX. Six fresh renders per
backend/case were deterministic and frame counts matched. Timed in-memory
throughput ranged around 34–36 times real time for Nuked and 186–343 times real
time for ymfm.

Those fixtures were generated by the engine, not captured from hardware. Their
old form omitted internally streamed DAC bytes, so generated audition files
were FM-only. That statement does **not** describe the current runtime:
production `playDac` callbacks have included real streamed DAC bytes since
`0ae29a261`. The experiment also used the current facade's one-address plus
34-data-hold clocks, but the two cores intentionally respond differently
within a native frame.

Raw music waveform correlation was 0.72–0.88; a diagnostic search within eight
samples found 0.96–0.99 at a four-to-six-sample lag. The three SFX were about
0.993 raw and 0.9995 at their best diagnostic lag. A single global gain and DC
removal were used for separate normalized-error and audition outputs. No delay
was applied to the primary metric or audition files. Correlation, gain fitting,
delay search, and level-matched A/B files are diagnostics, not proof of audible
or hardware equivalence. No listening sign-off was performed.

## Evidence limits and deferred work

The strongest evidence is the exact source and workspace pinning, raw logs,
separate process forks, warm-ups, wall and thread-CPU timing, CPU affinity,
deterministic rerenders, matching Java/C Nuked checksums, exact snapshot replay,
and active negative controls.

The gaps are equally important: one high-end noisy Linux host; no low-end,
Windows, or macOS data; different HotSpot/Graal patch levels; no full-game or
audio-thread deadline profile; no performance counters; stubbed ymfm timer and
busy callbacks; no status reads, IRQ, or CSM validation; no real PCM transfer,
resampling, scheduling, native snapshot lifecycle, packaging, or teardown; no
hardware-captured stream comparison; and no listening assessment.

## Ranked next experiments

1. **Profile and optimise the Java Nuked port first.** Keep the 732 bit-exact
   cases and adapter parity as non-negotiable gates, profile production-shaped
   service and DAC workloads, and optimise only measured Java hot paths. This
   has the lowest lifecycle and distribution risk. The achievable core and
   whole-engine speedups are unknown.
2. **Prototype batched native Nuked behind the same semantics.** The experiment
   shows a batched JNI bridge can preserve native Nuked's raw-core advantage on
   one Linux host. Using the same pinned core lowers synthesis-semantic risk,
   but native snapshot ownership, PCM transfer, teardown, packaging, LGPL
   compliance, and Windows/macOS support remain substantial. Production and
   whole-engine speedups are unknown.
3. **Evaluate ymfm only after complete physical capture exists.** ymfm was the
   fastest raw synthetic candidate, but its phase, scale, and subframe response
   differ. A serious evaluation needs complete physical-strobe replay,
   timer/busy/status behavior, mixed-output metrics, and listening tests before
   performance matters. Java-port, native-integration, and whole-engine
   speedups are all unknown.
4. **Do not assume the retired Genesis Plus GX-derived core can simply return.**
   `CREDITS.md` records that the former `Ym2612Chip` body descended from the
   GPGX/libvgm/MAME core, carried a non-commercial licence, and was removed from
   the tree when Nuked replaced it. Repository history and the surviving
   research example do not by themselves establish a redistributable,
   maintained rollback. Any resurrection starts with fresh provenance and
   licence review; this report makes no legal determination. Its current
   performance and integration cost are unknown.
5. **Treat a new clean-room core as long-horizon research.** It offers control
   over architecture and licensing inputs but requires independent hardware
   specifications, conformance vectors, synthesis work, optimisation, and
   listening validation. It is high cost and not an immediate 0.6 action; all
   speedups are unknown.

For 0.6, the release gates remain human listening QA of the release build plus
the fresh package, ordinary-suite, structural-guard, and trace no-regression
candidate run. At baseline `4296bc291`, the S3K frontier was service 1,569;
that historical point, the red Sonic 1 per-song windows, and the red Sonic 2
1-up window remain explicit parity research unless listening or candidate
testing exposes a release-impacting regression. Backend replacement, Graal
tuning, JNI production integration, timer/IRQ/CSM support, waveform equivalence,
and low-end/platform budgets are deferred.

The maintained ROM-free reproduction tool is
`tools/audio/fm-core-benchmark/`. It deliberately retains the Java/native
synthetic comparison, an order-, sign-, and channel-sensitive Java/C stream
hash, sample-wise exact snapshot replay, active controls, and provenance
checks, but not the Graal distribution, JNI spike, waveform output, or
machine-specific runner.

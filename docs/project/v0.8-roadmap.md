# OpenGGF 0.8 Roadmap — Graduate the added features

Updated: 2026-09-12. Shared implementation promoted to `develop` at
`11873ab36`; `next` advanced to `0.8.prerelease` at `3d0434661`. The
[rollover record](../architecture/validation/2026-09-12-release-rollover.md) owns
the measured ordinary/guard/package evidence; it does not certify campaigns.

0.8 follows the [0.7 complete-campaign baseline](v0.7-roadmap.md). It finishes,
qualifies and publishes the substantial modding, racing, creator and compatibility
work already implemented, then adds measured loading extensions and live FM
switching. Existing features continue to be regression-tested during 0.7; this
sequence defers final publication and broad compatibility claims, not their
maintenance. Features may remain experimentally available in 0.7 under the
[availability matrix](v0.7-roadmap.md#feature-availability-during-07); graduation
is a support/publication commitment rather than first availability. This
planning document does not itself authorize code removal, version bumps or
API publication.

## Milestone 0 — Accept the campaign baseline and bound feature scope

Start with completed stock-game lifecycle evidence and all four S3K terminal
chains from 0.7. Use those routes as consumers of loading, audio, save, rewind,
rendering and policy changes. Keep exact ordinary/guard/trace baselines and
supported package/viewport/team matrices. Do not reclassify landed modding,
editor, racing, widescreen, prepared loading or FM cores as new implementation.

The descriptor [mod-api-release-policy.properties](../../mod-api-release-policy.properties)
is the sole API version/publication authority. The baseline currently says
candidate `0.7.0` with no published baselines. Choose the release-aligned version
through that policy when implementation reaches publication; this roadmap's 0.8
name does not silently change the descriptor, signatures or compatibility rules.

Gate: freeze a tested campaign base and distinguish implemented, remaining
validation, new implementation and parked scope for each feature. Re-check source
when an older plan/backlog disagrees with the current implementation.

## Milestone 1 — Lock the game-policy architecture before Mod API publication

**Status:** planned; architectural direction approved

`GameModule` remains the composition and lifecycle root. The change introduces
a typed policy subtree rather than a superclass or a second competing root.

Target boundaries:

- Add an immutable `GamePolicies` aggregate for game-wide behavioral facts.
- Move `GameRules` ownership out of `PhysicsProvider`; camera, rings, objects,
  sidekicks, power-ups, and drowning rules are not children of physics.
- Keep narrow records such as `CollisionRules`, `CameraRules`, and `RingRules`
  as the consumers' dependencies rather than passing the entire aggregate.
- Separate audio behavioral rules from ROM-backed asset loading and stateful
  sound-driver construction. `GameAudioProfile.createSmpsLoader(Rom)` is a
  factory concern, even though the current profile also contains policy.
- Keep art, mappings, PLC/DPLC data, ROM offsets, registries, zone events,
  object-family behavior, and mutable session services with their existing
  smallest accurate providers or owners.
- Keep factories and lifecycle callbacks on module-owned runtime components;
  policies must be immutable and must not acquire session state.
- Support cross-game donation through explicit capability-specific composers.
  Do not add a generic mechanism that can arbitrarily replace any policy
  category.
- Preserve the rule-placement admission checklist and add guards against a new
  broad feature bag or game-name branches in shared runtime code.

This milestone must land before the first public Mod API baseline is published.
The candidate currently exposes gameplay policy types, so the migration must
update the recursive API inventory, creator documentation, sample mods, and
compatibility evidence together. Once a baseline is published, policy reshaping
must follow the published compatibility contract rather than silently rewriting
it.

Gate: all three stock modules expose the same typed policy shape; shared
consumers depend on their narrow category; supported donation combinations are
explicitly tested; invalid generic mixtures are not representable through a
public composer; and module/bootstrap, rewind, audio, trace, and Mod API guards
remain green.

## Milestone 2 — Extract Time Attack and multiplayer into a bundled mod

**Status:** planned for 0.8 after the campaign baseline and policy work, before
public API publication. Feature implementation already exists inside the engine;
this milestone changes its ownership and packaging, not its invention.

Time Attack and multiplayer ghost racing add no ROM behavior. They form a
large non-ROM gameplay surface now inherited by both development branches.
The base engine should carry ROM accuracy and the
mod framework; addon gameplay features belong in mods that consume that
framework. This work moves the feature out of the engine jar into a bundled,
first-party mod and treats it as the first real consumer of the Mod API.

### Historical measured surface at `next` 949e49072

These counts describe that commit. Re-measure the extraction surface at kickoff.

- `game/timeattack/` (32 files), `net/` (56 files, ~8.3k lines),
  `game/ghost/` (14 files), `tools/net/` and `tools/verifier/`; 82 test files.
- Engine coupling: ~183 lines in `GameLoop`, ~190 in `Engine`, ~85 in
  `MasterTitleScreen`, ~35 in `LevelRenderer`, plus `GameServices`,
  `GameStateManager`, and `GameplayModeContext` references. `GameLoop` and
  `Engine.draw` are already size-ratcheted by `-Pguards`.
- The feature's own design (`docs/architecture/designs/2026-07-04-multiplayer-time-attack-design.md`)
  is ghost-only with no physics synchronization, built on the shared
  `game/recording` stack that already exists on `develop`. The engine-facing
  contract is therefore small even though the feature is large.
- `GhostRenderRegistry` and `AttemptInputRecording` are already `@ModApi`
  roots; the remaining coupling is direct construction and frame wiring.

### Why before publication

`ModContext` currently registers game modules, patches, objects, characters,
art, zones, launch teams, input filters, and HUD profiles. It has no master-title
entry contribution, no frame-lifecycle hook, no overlay/HUD render contribution,
and no recording-consumer hook. Hosting Time Attack requires those seams, and
adding them changes the recursive signature inventory. Doing this after the
baseline is published would turn an ordinary refactor into a compatibility
decision under the release-line policy. If the framework cannot host the
project's own largest feature, it is not ready to publish.

### Target shape

- Engine keeps: `game/recording`, deterministic input recording and replay,
  `GhostRenderRegistry` as a generic ghost-sprite render seam, and the
  `ExternalContentPolicy` gate that keeps network and external content out of
  certifying trace/test sessions.
- Mod owns: track catalog, attempt state machine, split/delta HUD, `.ggfghost`
  store, identity, all of `net/`, room/vote/standings/spectate presentation,
  minimap and nameplates, and the Time Attack menu.
- Separate processes stay separate: master, relay, host, verifier, bot, and
  load-test tools move out of the engine artifact entirely.
- New Mod API seams, each generic rather than Time Attack shaped:
  1. master-title entry contribution (a mod-owned screen reachable from the
     master title, alongside the existing exclusive game-start destination);
  2. gameplay frame-lifecycle hook (level start, level end/finish, restart,
     pause) delivered after the engine's own frame step and never able to
     mutate gameplay state;
  3. overlay/HUD render contribution layered above the existing row-only HUD
     profile; and
  4. recording-consumer hook that receives finished deterministic recordings.
- Sample and Flappy mods remain outside the engine jar; verify the native S3K
  Tails retarget left no engine-side special cases.

### Constraints

- The extraction must not change native 320x224 timing, trace comparison, or
  any gameplay owner. Hooks observe; they do not drive.
- Rewind, save, and audio ownership stay with the engine; the mod uses the
  supported playable-subclass rewind surface and tagged saves like any other
  mod.
- Certifying sessions run with the mod absent, not merely disabled, so the
  engine's own tests do not depend on it.
- Arbitrary non-ROM team definitions are a candidate for the same treatment:
  keep the launch-team capability in the engine and move the non-ROM team
  list into a bundled mod so a stock install offers only ROM teams. Decide
  this separately; it does not block the Time Attack extraction.

Gate: `game/timeattack/`, `net/`, `game/ghost/` racing code, and the
`tools/net` and `tools/verifier` entry points are absent from the engine
artifact; the bundled mod builds through `ggfmod`, passes its own suite, and
reproduces the Milestone 5 Time Attack gate; the four new seams are in the
signature inventory with creator documentation and at least one non-Time-Attack
sample using each; `-Pguards` size ratchets for `GameLoop` and `Engine.draw`
tighten rather than loosen; and the public Mod API baseline is published only
after this lands.

### Native packaging decision belongs to this milestone

The [current native-build contract](../modding/index.md#native-builds-vs-the-jvm-jar)
rejects runtime-loaded code mods under closed-world AOT. Moving racing to a jar
therefore cannot automatically preserve its availability on native builds.
Decide and document this before extraction acceptance: either deliver racing as
an explicitly JVM-only bundled mod, or separately design and verify a supported
build-time native addon packaging path. The latter is additional implementation,
not an existing loader capability. Keep the stock engine artifact and certifying
sessions mod-free in either case; do not silently lose a previously advertised
platform feature or weaken code-mod rejection to make the package appear to work.

## Milestone 3 — Extend asynchronous ROM loading

**Status:** partially delivered through the 0.6 integration; wider extensions
planned for 0.8. Campaign-blocking correctness fixes remain 0.7 work.

Extend the delivered preparation paths to reduce remaining measured host frame
hitches by preparing ROM-backed assets on bounded workers
while the game executes existing PLC/decompression waits, fades, and title-card
loading transitions. Start with standalone object/boss art; extend incremental
queues only after the simpler path demonstrates a measurable benefit.

### Existing preparation and timing foundation on both development branches

`LevelLoadPreparer` already runs preparation on a daemon worker and joins the
result at installation, with synchronous fallback. `LevelManager` uses prepared
level builds and tilemaps; AIZ2 preparation already covers level decode, object
art and tilemaps across the fire event. The September 8 merge retained custom
module priority and rejects stale preparation at override/deferred boundaries.
Retain these implementations and their tests rather than rebuilding them. A
single retained pending slot does not alone prove all queued worker work and
bytes are bounded under repeated discard/resubmit; audit that separately.


Build on the existing simulated load-time and trace-timing infrastructure:
`HardwareTimingService`, `LoadTimeProfileFactory`, `ProfiledLoadTimeManifest`,
`RomWorkBudgetScheduler`, and recorded completion admission. This work already
separates CPU preparation from observable readiness. Preserve its configured
load-time profiles, native service budgets, and recorded completion boundaries
while moving eligible CPU preparation onto workers.

The existing timing owners continue to determine when completion is visible;
the new worker layer uses those waiting periods to prepare bytes. Host elapsed
time and worker completion order must not change simulated frame counts or
replace recorded lag/main-loop admission. Profile-based readiness applies only
to work submitted through the timing service; game-owned PLC and dynamic-art
lifecycles retain their own service rules. Audit each candidate's actual owner
before connecting it to workers, and preserve existing mode/fallback behavior.

This is an extension of the timing implementation already promoted to
develop. At kickoff, inventory its current game/kind support and fixture coverage separately; the
cross-game contract alone does not establish implemented or tested coverage.

### Ownership and timing constraints

- Separate host preparation from game-visible submission, service, completion,
  and rendering. A cache/prefetch operation must not invent a ROM queue job or
  make a future submission visible early.
- Workers consume immutable ROM data and produce independently owned CPU-side
  results. Keep queue mutation, gameplay changes, art registration, destination
  tile writes, renderer refresh, and GL uploads on their existing owning thread.
- An early worker result waits for the ROM-modeled service boundary. Preserve
  FIFO order, clear-versus-append behavior, incremental pattern/module delivery,
  destination overwrites, and all observable queue/decoder progress. A single
  `Future.isDone()` flag cannot replace the resumable queue model.
- If preparation misses its deadline, wait at the required host boundary rather
  than advance gameplay or insert extra emulated wait frames. This fallback can
  still hitch. Any responsive presentation during the wait needs an explicit
  input/audio/clock policy that preserves deterministic replay.
- Bound pending jobs, decoded bytes, and cache retention. Identify results by
  ROM/content identity and the owning session/transition generation; reject
  obsolete completions after cancellation, restart, ROM replacement, or rewind.
- Rewind captures deterministic modeled progress, not worker scheduling. Restores
  may reuse valid immutable results or re-prepare them without allowing the host
  completion order to change gameplay.
- Preserve the [hardware-timing authority contract](../architecture/designs/2026-07-27-cross-game-hardware-timing-trace-contract.md):
  recorded timing may admit only matching, prepared, production-submitted work.
  Worker timing never becomes trace authority or supplies gameplay values.

### Delivery sequence

1. Inventory delivered preparation paths and remaining synchronous work on the
   completed campaign baseline. Measure first-use art loads and existing waits:
   CPU preparation,
   queue service, GPU upload, allocation, retained bytes, and frame-time tails.
   Use the integrated `develop` performance fixes as the baseline, not new scope.
   Include the existing load-time profiles and recorded admission in that
   baseline; identify reusable preparation boundaries before adding worker APIs.
2. Reuse existing pure CPU preparation/builders. Extend only remaining
   synchronous object/boss sheets with a bounded worker during production
   loading transitions.
   Evaluate earlier cache preparation without changing ROM submission timing.
3. Prove early/late completion, cancellation, failures, restart, and rewind on
   this path before considering incremental Nemesis/PLC and Kosinski/KosM queues.
   Preserve their distinct service and partial-visibility contracts.
4. Extend only where measurements justify it, with per-game owners supplying
   semantic scheduling rules rather than shared game/zone-name branches.

Starting points to inspect are `Sonic3kPlcLoader.preDecompress`, the deferred
level-resource owners, and the preparation/readiness separation in the hardware
timing service. Distinguish delivered AIZ2 background preparation from remaining
queue/art
paths; re-check each current owner at kickoff. Correctness and measured benefit
are prerequisites for extension, not a promise of completely hitch-free loading.

Acceptance: compare synchronous and asynchronous results across representative
loading transitions and multiple recordings, in both supported live load-time
modes and recorded-timing replay, including deliberately reordered,
early, late, failed, and cancelled worker completions. Require identical asset
bytes, queue state, partial tile visibility, input/audio progression, and rewind
outcomes; no new trace divergences; bounded memory and shutdown; and measured
improvement in loading-frame latency or allocation. Run the relevant art/mapping,
queue, timing-authority, rewind, ordinary-suite, and fresh-JVM guard checks. Do
not publish an async-loading or hitch-free claim before this evidence exists.

## Milestone 4 — Live FM core switching

**Status:** planned for 0.8; fast/accurate cores and device-start selection are
already delivered. Qualify campaign audio restoration in 0.7 first.

0.6 ships two FM cores behind `audio.fmCore`: `accurate` (the cycle-exact
Nuked-OPN2 port, about 1 ms per frame on the audio thread) and `fast` (the
clean-room register-level core, about 0.15 ms, the default; 178 of 178 oracle
vectors within tolerance). Changing the setting takes effect at the next
physical device, so comparing the two by ear means restarting. This item makes
the choice a live, shippable option with one core running in steady state.

### Proposed design

The cores cannot share internal state: Nuked's is cycle-level, the fast core's
is frame-level, and translating between them would require reading the port's
synthesis state, which the fast core's clean-room rule forbids. They do accept
the same register stream, so a standby core is a cold object plus the live
register image.

- A `FmChip` wrapper owns the active core and records the live register image
  (both ports, 256 registers each, DAC enable and data, mutes, pan) through the
  existing chip write observer. Measure register-image tracking overhead; do not
  assume zero steady-state cost.
- On a switch request the wrapper resets the standby core, replays the image in
  canonical order (voices, levels, pitches, pans, LFO and timers, then key-ons)
  and runs both cores.
- During the warm-up the standby's sustained notes attack and decay to the live
  core's level. The wrapper correlates the two outputs over a short window and
  crossfades over about 20 ms once they agree, or after a 500 ms timeout; the
  old core is then dropped. Both cores run only for that fraction of a second.
- Rewind carries the active core's snapshot plus the core id, so a restore
  across a switch reinstates whichever core was live at that time.
- The setting stays `audio.fmCore`; a debug hotkey (off by default) flips it in
  play; the physical audio parity capture keeps refusing the fast core.

### Listening targets to prove

Reconstructing registers does not reconstruct oscillator/envelope history.
Sustained notes can re-attack; the proposed warm-up/crossfade must be tested for
perceptible discontinuities, percussion, DAC/SFX, fades and overrides. A 20 ms
crossfade and 500 ms timeout are design candidates, not proven transparent
switching. Keep only one core running in steady state; measure the temporary
dual-core CPU peak and slower-core underrun risk on supported machines.

### Acceptance

- A scripted-DSP delegation test: every write, DAC call, mute and reset reaches
  the active core and the register image; the output follows the selection.
- A switch-during-sustain oracle test: switch in the middle of a held chord
  with LFO on and check the crossfaded output against a never-switched run of
  the destination core using measured waveform/spectral bounds plus listening
  checks. Establish achievable criteria before implementation rather than
  assuming sample-exact convergence from a register image.
- A rewind round-trip across a switch.
- The fast-core corpus, the ordinary suite and the trace suite unchanged with
  the wrapper in place and `fast` selected.
- CONFIGURATION.md and the controls guide updated; the listening-test plan
  gains an A/B step that no longer needs a restart.

### Separately acceptable first step

If the full design slips, apply the switch at the next music start (level load,
act change, 1-up return) with no warm-up or crossfade. Re-estimate and validate
this independently;
the setting reads "takes effect at the next track", and it must not be described
as arbitrary mid-track live switching.

## Milestone 5 — Qualify and publish the staged feature set

**Status:** implemented in substantial part; release validation remains

The following workstreams, promoted from next into develop, are part of 0.8
feature graduation.
Their presence in branch history is not by itself a release claim.

### Modding and creator tooling

- Mod API 0.7 candidate, release-line policy, recursive signature inventory,
  trusted code mods, patch composition, music overrides, ROM-art intake,
  owner-tagged characters, custom/standalone games, tagged saves, and explicit
  gameplay policies.
- Deterministic `ggfmod` tooling, hardened Tiled TMX import, creator handbook,
  compatibility guide, and CI-built sample gallery.
- Editor object/ring placement, collision and solid-index editing, library
  panes, versioned saves, and full-level export foundations.

Gate: publish the first API baseline only after Milestones 0, 1 and 2; build and
run every maintained sample; validate SDK/Javadoc packaging and native-image

### Time Attack and multiplayer

- Solo Time Attack with curated tracks, deterministic input recordings,
  best-ghost racing, split deltas, instant retry, and Ed25519 player identity.
- Multiplayer race protocols, authenticated rooms, relay/ghost transport,
  standings, voting, spectating, minimap/nameplate presentation, and verified
  service foundations inherited by both development branches.

Gate: local solo play remains deterministic and offline-safe; LAN and hosted
paths have bounded failure behavior and security review; no network or external
content is enabled during certifying trace/test sessions; service-dependent
features degrade honestly when services are unavailable.

This workstream is scheduled to leave the engine artifact and ship as a bundled
mod before the Mod API baseline is published; see
[Milestone 2 — Extract Time Attack and multiplayer into a bundled mod](#milestone-2--extract-time-attack-and-multiplayer-into-a-bundled-mod).
The gate above applies to the mod once extracted.

### S3K, rendering, and compatibility foundations

- Late-route zone, object, boss, and transition groundwork; super-emerald
  progression/sanctuary; Super Tails flock; and Hyper Sonic effects.
- Arbitrary-sidekick ownership work across S1, S2, and S3K, plus supported
  widescreen object/render boundaries.
- Live viewport capture, render-copy harnesses, allocation reductions, and
  S3K trace-parity improvements.

The already-delivered widescreen contract is intentionally tiered:

| Logical viewport | Retained support |
|---:|---|
| 320x224 | Exact native invariant and trace-comparison authority |
| 352x224 | Supported width-derived presentation |
| 400x224 | Primary supported widescreen target |
| 528x224 | Best-effort smoke tier with automated bounds and visual evidence |
| 800x224 | Exploratory; no full-support claim |

Ordinary UI and HUD surfaces, title cards, results, endings, diagnostics, all
three special-stage providers, width-sensitive scene effects, and trace-video
presentation use the live logical viewport. Native-authored special-stage
foregrounds remain centered in a 320px safe area, and capture changes only
presentation dimensions: trace comparison, gameplay state, timing, and ROM
world boundaries remain native.

Gate: retain each advertised behavior under focused tests and visual evidence;
do not let compatibility or viewport support change native 320px timing; and
do not describe a partially gated zone or trace as complete. Widescreen support
must retain focused 320/352/400 coverage, semantic 320/400/528 AIZ transition
captures with equal frame counts, and explicit best-effort/exploratory wording
for 528/800.

## Original commitments and demand-driven follow-ons

The [mod backlog](../modding/BACKLOG.md) preserves original-scope commitments and
parked decisions. Its current disposition must reflect later implementation:
S3K's bounded format-v2 adapter is delivered; base-game streamed SFX overrides
and the S1 new-zone adapter remain scheduled follow-ons. Neither standalone SFX
nor the S2 zone adapter proves those missing host contracts.

Schedule the two outstanding original commitments in 0.8, each with its own
bounded design and acceptance from the
[follow-on plan](../architecture/plans/2026-07-13-mod-support-original-scope-follow-ons.md).
Review their proposed public signatures/formats alongside Milestones 1 and 2
before publication. SFX work reuses audio lifecycle evidence but remains separate
from FM synthesis switching. S1 zone work reuses the settled policy/load boundary
without broadening stock-game loading. If either commitment slips, explicitly
reschedule it and narrow the release claim; do not silently park or drop it.

Native Knuckles-in-Sonic-2 remains a separate original ROM lock-on target.
Its implementation/parity programme is a 0.8 follow-on, not proof supplied by
S3K-donated character support and not a 0.7 three-stock-game gate. Re-establish
its current source/trace status before scheduling implementation; use its own
ROM/disassembly differences and route evidence.

Broader chip/SMPS parity and listening validation remain tracked work. Prioritize
observed campaign and advertised feature defects; live core switching is not a
substitute for audio parity. Keep quantitative and listening claims separately
supported by the existing audio evidence owners.

Hot reload, external studio UI, broader S3K stock-event mod profiles, editor live
re-apply, arbitrary policy mixing, and other parked items do not automatically
become 0.8 promises. Follow the backlog's demand triggers and
[GUI evaluation](../modding/GUI_TOOLING_EVALUATION.md). Actworks and cowtree remain
independent projects, with no OpenGGF release dependency.

## Dependencies and delivery order

1. Accept 0.7's complete-game baseline and audit delivered feature scope.
2. Design policy changes and first-party mod hooks together. Land the narrow
   policy migration, then extract racing, including its package/platform choice.
3. Review outstanding SFX/zone API and format additions before freezing the
   candidate. Keep each feature's implementation and acceptance separately owned.
4. Extend loading at measured remaining bottlenecks and implement FM switching
   against the campaign lifecycle corpus. These need not wait for each other;
   changes to common device/rewind/transition owners must be reconciled in order.
5. Run the complete supported feature/route matrix, samples, SDK/Javadoc and
   package checks. Publish the API only after all public surface changes land.

The extraction and policy work share API/inventory consumers and should be
planned together. Loading and live FM switching share regression infrastructure,
not a mandatory implementation dependency; do not combine them into one risky
runtime rewrite. Existing editor/widescreen/team work principally needs coverage
against completed routes, not another round of broad new features.

## Milestone 6 — Release and publication

Require JDK 21 ordinary tests, a separate fresh-JVM guard run, unchanged required
campaign chains, focused feature/rewind/audio/rendering tests, maintained sample
builds, SDK/Javadoc checks and explicit native/JVM packaging results. Use direct
Maven and worktree-local `target/`; retain command, commit, reports, inspected
skips and identity-based failure comparisons. No new/worsened baseline failure,
and no unresolved failure in an advertised release gate, is acceptable.

Require offline-safe solo racing, tested LAN/hosted failures, service security
review and mod-free certifying engine sessions. Record the bundled mod's native
availability decision. Complete measured loading and FM-switch acceptance, or
explicitly move unfinished optional work to a named follow-up before finalizing
release prose; never imply the crossfade or broad async support shipped.

Update creator/player/configuration/compatibility/release documentation and
publish the first API baseline only when policy, racing hooks, retained samples
and planned public additions agree. Existing campaign regression debt cannot be
hidden by feature-only tests, and already-published compatibility rules apply to
any later API change.
